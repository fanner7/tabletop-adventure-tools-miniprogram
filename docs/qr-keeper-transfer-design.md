# 调查员角色卡「二维码直传」数据格式设计

> 研究文档 · 2026 · 桌面冒险工具集
> 目标：COC 调查员工具把角色卡摘要编码进分享卡片图片角落的二维码，守密人工具扫码导入。
> 前置研究：BLE 直传可行但工程成本高、PC 端受限；二维码单向传输与本场景（玩家→守密人）完全匹配。
> **实现状态：已实现（utils/keeper-qr.js + 分享卡集成 + 守密人扫码导入 + 单元测试），本文档为最终规格。**

---

## 1. 设计目标与约束

| 约束 | 数值 | 来源 |
|---|---|---|
| 二维码嵌入分享卡角落，边长 267px | 模块 ≥ 2.8px → 版本 ≤ v17 | 卡片画布宽 750px，footer 区域实测 |
| 微信聊天转发会压缩图片（JPEG 有损） | 纠错级别 ≥ Q（25%），大载荷降级 M | 二维码标准实践 |
| 单码容量预算（**实测**，含模式/长度开销） | **Q 级 ≤ 322 B（v16）/ M 级 ≤ 450 B（v16）** | 生成器实测（见 §7） |
| 守密人端渲染字段 | 见 §5 兼容矩阵 | coc-keeper.wxml 实测审计 |
| 项目无 npm 依赖 | 编解码为单文件纯 JS | 项目现状 |

## 2. 体积实测（真实完整卡，60 技能表 / 114 职业 / 60 武器）

用测试脚手架（`tools/test/harness.js`）走完整建卡流程生成真实 `charData` 测量：

| 方案 | 真实卡 | 满卡压力 | 结论 |
|---|---|---|---|
| 全量 JSON（现状导出，含背景文本） | 7655 B | — | ❌ 单码放不下 |
| 精简 JSON（短键，仅守密人字段） | 1395 B | — | ❌ 超过 v20-Q 上限 |
| 管道格式·技能中文名内联 | 815 B | 868 B | ⚠️ 勉强 v20-Q（97 模块，太密） |
| 索引化·全部 59 技能 | 455 B | 496 B | ⚠️ Q 级需 v20（97 模块） |
| **最终规范 v2（技能/武器双索引 + 解码端反推基础值）** | **233 B**（3 武器） | ~460 B | ✅ **Q 级 v13（69 模块，3.5px/模块）** |

**三个关键设计决策：**
1. **技能用 `ALL_SKILLS` 表下标编码**（每个技能 ~5 B，中文名方案 ~15 B）；
2. **载荷只携带「投入过点数」或「携带专攻」的技能**；未投入的基础值技能由解码端用 `母语=EDU`、`闪避=DEX/2`、`专攻子项 base` 规则反推——59 项技能重建后与原卡**逐项一致（差异 0）**，载荷从 455 B 降到 ~200 B；
3. **武器同样索引化**（`w<idx>` 查 `WEAPONS_1920S` 还原 技能/射程/贯穿/次数/弹药/故障 全部字段，自定义武器才内联）——武器段从 ~40 B 降到 ~10 B，守密人武器表 8 列完整。

## 3. 载荷格式规范 v2

```
C7K2|<fp>|<name>|<player>|<occ>|<era>|<a9>|<d6>|<skills>|<weapons>*<crc>
```

| 段 | 含义 | 示例 | 说明 |
|---|---|---|---|
| `C7K2` | 魔数 + 格式版本 | `C7K2` | 版本可演进，v2 起 |
| `<fp>` | 技能表+武器表指纹 | `13dc` | CRC16(技能名拼接 + `\|` + 武器名拼接)；两张表任一漂移都明确报错 |
| `<name>` | 调查员姓名 | `哈维·怀特` | UTF-8，保留字符转义 |
| `<player>` | 玩家昵称 | `小明` | 可空；同名调查员区分用 |
| `<occ>` | 职业 | `律师` | 可空（空则守密人端不显示职业行） |
| `<era>` | 时代 | `1920s` | 可空 |
| `<a9>` | 九属性 | `60,65,70,55,80,62,75,85,50` | 固定顺序 str,con,dex,app,pow,siz,int,edu,luck |
| `<d6>` | 衍生值 | `12,80,16,0,0,8` | hp,san,mp,db,build,mov（db 可能含 `+`/`-`） |
| `<skills>` | 技能表，逗号分隔 | `0=45,47.0=25,...` | 见 §3.1；仅投入/带专攻技能 |
| `<weapons>` | 武器表，分号分隔 | `w26;w12;c秘制毒药瓶=...` | 见 §3.3；表内武器索引化，自定义武器内联 |
| `*<crc>` | 整段校验 | `*e627` | CRC16，4 位 hex；防止错码/截断 |

**转义**：所有文本字段中的 `| ; , = .` 一律替换为 `_`（解码端不还原，显示为下划线即可；专攻文本理论上才可能含这些字符，属罕见场景）。

### 3.1 技能编码 `<skills>`

每条 `code=total`，total 为技能总值（0-99）。**编码规则**：`total ≠ base`（投入过点数）**或** `displayName ≠ name`（携带专攻）的技能才编码；其余技能解码端反推。

| 形态 | 含义 | 示例 |
|---|---|---|
| `idx=total` | 普通技能：`ALL_SKILLS[idx]` | `0=45` → 会计 45%（基础 5 + 40） |
| `idx.opt=total` | options 型槽位：`spec.options[opt]` | `47.0=25` → 格斗①（斗殴）25% |
| `idx.text=total` | text 型槽位：专攻文本内联 | `56.拉丁语=1` → 外语①（拉丁语）1% |
| `n<name>=total` | 兜底：不在表中的自定义技能名 | `n驯鹰=20` |

**解码端反推规则**（与建卡器 `buildPreviewSkills` 完全一致，实测 59 项技能零差异）：
- `母语` base = EDU；`闪避` base = ⌊DEX/2⌋；options 专攻取子项 base；其余取表 base；
- 遍历 `ALL_SKILLS`：载荷有 `idx` → 用载荷 total；否则 `base > 0` → 用 base；否则跳过（base=0 且未投入，建卡器同样不显示）；
- 槽位技能只要有专攻就编码（即使未投入）——专攻影响 base 与显示名，必须显式携带；
- 解码产物携带重建的 `skillSpecs`，保证「解码→重编码」幂等（单元测试断言）。

### 3.3 武器编码 `<weapons>`

武器段分号分隔，两条路径（与技能同理：表内索引化，自定义内联）：

| 形态 | 含义 | 示例 |
|---|---|---|
| `w<idx>` | 表内武器：`WEAPONS_1920S[idx]`，解码端查表还原 name/skill/skillId/damage/range/impale/attacks/ammo/malfunction 全部字段 | `w26` → .38(9mm)左轮手枪（手枪/1D10/15/√/1(3)/6/100） |
| `c<name>=<skill>=<damage>=<range>=<attacks>=<ammo>=<malfunction>=<impale>` | 自定义武器全字段内联（字段缺失解码端按 WXML 兜底补 `——`） | `c秘制毒药瓶=科学=1D4=投掷6码=1=一次性=100=×` |

- 解码端为每件武器生成 `_id`（守密人 WXML 武器行 `wx:key="_id"` 需要）；
- 武器名在表中唯一（数据完整性测试保障），`w` 前缀按名查索引；
- 表指纹 `fp` 已覆盖武器名列表，武器表内容/顺序漂移同样触发 TABLE 错误。

### 3.4 完整示例（真实卡实测，233 B，3 武器：2 表内 + 1 自定义）

```
C7K2|13dc|哈维·怀特|小明|律师|1920s|60,65,70,55,80,62,75,85,50|12,80,16,0,0,8|0=45,4=55,5=55,8=50,10=55,20=50,22=50,47.0=25,50.0=20,53.4=5,56.拉丁语=1|w26;w12;c秘制毒药瓶=科学=1D4=投掷6码=1=一次性=100=×*e627
```

（233 B；解码对照节选：
- 技能：`0=45` → 会计 45%；`10=55` → 信用评级 55%（基础 0，投入）；`22=50` → 闪避 50%（DEX/2=35+15）；`47.0=25` → 格斗①（斗殴）25%；未编码的 `人类学 1%`、`母语 85%` 等由解码端反推
- 武器：`w26` → .38(9mm)左轮手枪；`w12` → 小型刀具(弹簧折叠刀等)；`c…` → 自定义武器，8 字段全部还原
- 守密人武器表 8 列（武器/技能/伤害/射程/贯穿/次数/弹药/故障）不再有缺失）

## 4. 编码 / 解码契约

### 4.1 共享模块 `utils/keeper-qr.js`（单文件，纯 JS，无依赖）✅ 已实现

```js
encodeKeeperQR(charData) → string   // coc7-gen 分享卡调用
decodeKeeperQR(text)    → { player } | { error: 'CRC'|'TABLE'|'FORMAT'|'VERSION' }
drawKeeperQR(ctx, text, x, y, size) // 分享卡画布直绘（不重置画布）
crc16 / tableFingerprint / getSkillBase   // 基础值反推（母语=EDU、闪避=DEX/2、专攻子项）
```

- 内部 require `../pages/coc7-gen/data/skills.js` + `../pages/coc7-gen/data/weapons.js`（单一数据源；指纹校验兜底版本漂移）
- 二维码矩阵来自 vendored `utils/weapp-qrcode.js`（MIT，仅补丁导出 `QRCode/utf16to8/QRErrorCorrectLevel`）

### 4.2 解码产物（与守密人 WXML 字段逐项对齐）✅ 已实现

```js
{
  charInfo:  { name, player, era },
  selectedOcc: { name },                      // 载荷为空时省略
  attrValues: { str, con, dex, app, pow, siz, int, edu, luck },
  attrDisplay: [ {label:'力量 STR', value, hard, extreme} ×9 ],   // 属性九宫格
  derived:   { hp, san, mp, db, build, mov },
  derivedItems: [ {l:'生命 HP',v}, {l:'理智 SAN',v}, {l:'魔法 MP',v},
                  {l:'伤害加值',v}, {l:'体格',v}, {l:'移动力',v} ], // 状态区
  skillSpecs: { '格斗①':'斗殴', ... },        // 重建（重编码幂等依赖此字段）
  sortedSkillsByCat: [ {catName, cat, skills:[{name,displayName,base,total,hard,extreme}]} ],
  charWeapons: [ {name, skill, skillId, damage, range, impale, attacks, ammo, malfunction, _id} ],
  source: 'qr', qrVersion: 2,
}
```

**兼容性结论**：产物通过现有导入校验（`attrValues && charInfo`）；守密人 WXML 全部渲染分支（卡面状态色、属性格、技能检定点击、**武器表 8 列**、战斗轮 DEX 排序）所需字段均已覆盖；`_id` 满足武器行 `wx:key`；未传字段（`playHP`、`majorWound`、背景文本块等）在 WXML 中均有 falsy 兜底或 `wx:if` 隐藏，无副作用（与现有 NPC 速建的最小对象同机制）。

## 6. 守密人端接入（coc-keeper）✅ 已实现

导入弹窗新增两个入口（用户需求：摄像头直扫 + 相册扫码）：

```
📷 摄像头扫码导入 → wx.scanCode({ scanType:['qrCode'], onlyFromCamera:true })
🖼 相册二维码导入 → wx.scanCode({ scanType:['qrCode'], onlyFromCamera:false })   // 扫码页可切相册选图
  → decodeKeeperQR(result)
  → 错误分支：CRC→'二维码读取不完整，请重试'；TABLE/VERSION→'请更新小程序'；FORMAT→'不是有效的调查员二维码'
  → 成功→共用 importPlayerObject(obj)（同名去重 + 入队 + 保存，剪贴板/二维码同一路径）
  → showModal '继续扫码导入下一位调查员？'（连续导入）
```

> 注：`wx.scanCode` 无"直接打开相册"的 API，相册入口打开的是扫码页（页面自带相册图标可选图）；PC 端微信不支持 `wx.scanCode`，PC 守密人仍走剪贴板通道。

## 7. 健壮性与版本演进

| 风险 | 对策 |
|---|---|
| `ALL_SKILLS` / `WEAPONS_1920S` 表顺序/内容漂移 | `<fp>` 指纹覆盖两表，不匹配给明确提示；数据文件头部已有"请勿手改"约束 |
| 转发图片被压缩损坏 | Q 纠错（大载荷 M）+ 白色静区 + 大模块；主路径为屏幕直扫 |
| 自定义专攻文本含分隔符 | 统一转义 `\|;,=.` → `_` |
| 基础值反推规则漂移（母语/闪避/专攻 base） | 与建卡器 `getSkillBase` 等价实现 + 单测断言逐项一致；规则变更时 bump 载荷版本 |
| 未来扩展（游玩状态同步、更多字段） | 魔数版本位 `C7K3` 演进，解码端按版本分发 |
| PC 端守密人（wx.scanCode 不可用） | 保留剪贴板 JSON 全量导出通道，双通道并存 |

**容量表勘误**：初版文档引用的 v13~v20 容量（如 v16-Q 516B）偏大，实测生成器（含模式/长度开销）为 v16-Q 322B、v16-M 450B、v17-M 504B、v20-Q 482B。本方案通过"仅投入技能"编码把典型载荷压到 199B，Q 级 v12 即满足，容量不再是瓶颈。

## 9. 备选方案否决记录

- **BLE 直传**：可行但需外设+中心双角色、分包 ACK 协议、Android 权限坑、iOS 前台限制、PC 不支持——成本高收益与二维码相同
- **精简 JSON 短键**：1395 B，超 v20-Q 单码上限；若拆多码则体验劣化
- **中文名内联管道**：815 B → v20-Q 97×97 模块，嵌入 267px 后仅 2.7px/模块，压缩后不可靠
- **云中转分享码**：跨平台最优但需联网 + wx.cloud 配置，与"离线即扫"目标不符；可作后续补充通道
